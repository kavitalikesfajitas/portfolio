# Optimizely Singleton Provider

**Role:** Frontend / Platform Engineer  
**Tech Stack:** Next.js · TypeScript · Optimizely · React

---

The Optimizely Node SDK is meant to run as one long-lived client per process: you seed it with a datafile, turn on `autoUpdate`, and let it refresh on an interval you choose. In a normal Node service you create that client when the process starts and keep reusing it. In Next.js you do not get that for free. The framework does not expose a built-in singleton for server-side SDKs, and initializing the client next to routes or render paths can mean Optimizely work (and traffic) scales with page hits instead of with a deliberate refresh policy.

This piece is about how we wired that behavior anyway for a standalone Next app running in containers: we store the client on `global` using a small `GlobalRef` helper keyed with `Symbol.for(...)`, so every part of the same Node process resolves the same instance. We prefetch a datafile at build time into `fallbackDatafile.json` via `next.config.mjs`, so a cold start is not chained only to the CDN being up. Polling stays on the server SDK; the React integration receives the datafile as props and runs with client-side auto-fetch off so we are not running two refresh loops. After we landed that split, a production incident validated it—the runaway pattern was not the backend singleton path, it was duplicate client-side behavior.

## Overview

**What we shipped:**

- **`GlobalRef` + `Symbol.for(...)` on `global`** — one storage key per process; client created once when the provider module loads at pod startup, not per request.
- **Build-time prefetch** — `next.config.mjs` calls a helper that writes `fallbackDatafile.json` so boot is not only CDN-dependent.
- **Backend owns polling** — server SDK uses `datafileOptions.autoUpdate` + `updateInterval`; React gets a passed-in datafile with `autoUpdate: false` so the browser does not run a second polling loop.

## `GlobalRef` and startup init

The client lives in a small utility that stores a value on `global` under `Symbol.for(uniqueName)`:

```typescript
export class GlobalRef<T> {
  private readonly sym: symbol;

  constructor(uniqueName: string) {
    this.sym = Symbol.for(uniqueName);
  }

  get value() {
    return (global as any)[this.sym] as T | undefined;
  }

  set value(value: T) {
    (global as any)[this.sym] = value;
  }
}
```

`Symbol.for` registers the key in the global symbol registry, so every import path in that process resolves the same `global[sym]`. That is the workaround: Next does not provide a singleton primitive for long-lived SDKs; you anchor state on `global` explicitly.

Bootstrap only runs when the value is missing:

```typescript
export const optimizelyInstanceGlobal = new GlobalRef<Optimizely.Client>(
  "optimizelyClient",
);

export const setOptimizelyClient = () => {
  if (!optimizelyInstanceGlobal.value) {
    optimizelyInstanceGlobal.value = Optimizely.createInstance({
      sdkKey,
      datafile: fallbackOptimizelyDatafile,
      odpOptions: { disabled: true },
      datafileOptions: {
        autoUpdate: true,
        updateInterval: OPTIMIZELY_REFRESH_INTERVAL,
      },
    }) as Optimizely.Client;
  }
};
```

After that, one instance owns background refresh. Instrumentation can confirm a single init at startup; it does not turn Next into a language-level singleton guarantee—it just verifies your hook ran once.

## Fallback datafile (build + runtime)

`next.config.mjs` awaits a prefetch before returning config:

```javascript
try {
  await preFetchOptimizelyDatafile();
} catch (error) {
  console.error(
    "Error pre-fetching Optimizely Datafile Fallback File:",
    error,
  );
}
```

Helper fetches from Optimizely’s CDN and writes `fallbackDatafile.json` next to the provider code.

**Sequence:** build writes the file → process starts and creates the client from that snapshot → SDK refreshes in the background on your interval (e.g. `180000` ms for three minutes). Staleness is a knob you set, not a side effect of how often pages render.

## Server vs client

**Server:** the shared client waits with `onReady()` and evaluates flags (e.g. an `enabled` route).

**Client:** `createInstance` from `@optimizely/react-sdk` with the injected datafile and `datafileOptions: { autoUpdate: false }` so only the backend drives datafile freshness.

```text
Build     → fetch datafile → fallbackDatafile.json
Pod boot  → one server client from fallback → autoUpdate on interval
Requests  → reuse server client; pass datafile into React provider; no client-side polling
```

## Production incident (June 2025)

An internal June 2025 post-mortem on production slowness traced growing outbound traffic to Optimizely (Cloudflare IPs). Load testing and instrumentation showed the **backend** path initialized once per pod and was not the runaway source. The **frontend** SDK’s default background behavior, even with cleanup hooks, still correlated with growing traffic. The fix aligned with this architecture: strip frontend polling, pass the server datafile into App Router pages, and disable automatic client-side datafile fetching. Traffic stabilized; flags kept working.

`autoUpdate: false` on the React side is not only fewer bytes—it is the split that incident validated: one lifecycle for datafile refresh on the server, consumption only in the browser.

## Outcomes

- Vendor traffic decoupled from page visits: refresh on a **pod + interval** model instead of **per visit**.
- Fewer duplicate fetches: no parallel client polling loop.
- Safer boot: on-disk fallback when the CDN is unhappy.
- Incident response confirmed where not to duplicate Optimizely’s background work.

## Reuse and follow-ups

**Same idea for** other long-lived SDKs (flags, remote config, anything with a polled document).

**Recipe:** one process-scoped instance, seed from disk or build, background refresh on your policy, thin client that does not repeat the polling.

Newer Next features (`fetch` caching, `revalidateTag`) might offer another way to stage datafile freshness later; this build predated leaning on that. The problem then was simpler: stop refetch storms from traffic and own the lifecycle explicitly.
