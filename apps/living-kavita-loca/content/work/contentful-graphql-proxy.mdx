# Contentful GraphQL Proxy

**Role:** Lead Engineer / Maintainer  
**Tech Stack:** TypeScript · Node.js · GraphQL · Apollo Server · Express · Redis · AWS

---

## Overview

This work started from a day-to-day friction: teams were integrating against content as if it were a simple HTTP surface, but every real read was **GraphQL over POST** to Contentful. That mismatch made **query and schema iteration** harder than it needed to be.

I first shipped the pattern as a **Next.js Pages API route**—Apollo Server in front of Contentful with a checked-in schema and executor. I then **extracted the design** into a standalone **Express** service in my own monorepo: dedicated **`POST /contentful/graphql`**, optional **Redis** for a shared response cache (versus in-process LRU on the serverless route), **health checks**, CORS, and CI-friendly packaging.

## The Challenge

- **Mental model mismatch** — Call sites behaved like “hit this REST-ish endpoint,” while the implementation was always **POST + GraphQL** to Contentful.
- **Slow query churn** — Evolving operations, typings, and cache defaults was painful without a single, intentional BFF.
- **Cache topology** — In-process caching worked for a single Node instance; a shared **Redis** layer was the next step for consistent hits across replicas and deploys.
- **Operational clarity** — We needed a small surface (`/contentful/graphql`, `/contentful/health`) and sane defaults for TTLs and telemetry.

## Solution

### From Next.js route to standalone service

The core idea stayed the same: **load Contentful’s schema from the repo**, **wrap** it, and **delegate** execution to Contentful’s HTTP API with a bearer token. The standalone service keeps that contract but moves it off the web app and into a long-lived process where **Redis-backed Apollo caching** is a first-class option.

```typescript
const executor = buildHTTPExecutor({
  endpoint: CONTENTFUL_GRAPHQL_BASE_URL,
  method: "POST",
  timeout: 5000,
  headers: { Authorization: `Bearer ${process.env.CF_DELIVERY_CONTENT_TOKEN}` },
  retry: 1,
});

const schema = wrapSchema({
  schema: contentfulSchema,
  executor,
});
```

### Caching and observability

- **Apollo Server** with **cache-control defaults** (Contentful’s schema does not ship cache hints; defaults keep behavior predictable).
- **`response-cache`** so successful query results are cached in line with those policies.
- **Redis or in-memory** cache implementation behind Apollo’s key-value cache interface, selectable per environment.
- Optional **OpenTelemetry-style** Apollo plugin hooks for production metrics when enabled.

### Delivery

- **`GET /contentful/health`** for probes and sanity checks.
- **CORS** configured for known storefront origins.
- **HTTPS in local dev** (optional mkcert paths) when frontends require a trusted origin.

Qualitatively, the extracted service made it easier to **iterate on GraphQL operations**, **share cache state across instances**, and **operate the Contentful edge** as its own deployable unit.

## Key Learnings

- **Name the integration honestly** — When the wire protocol is GraphQL POST, tooling and ownership should match, or iteration cost stays hidden.
- **Schema-in-repo + executor** — Treating Contentful as an implementation detail behind a stable local schema speeds up reviews and codegen.
- **Cache defaults matter** — Without explicit cache policy on the upstream schema, **explicit server-side max-age** and response caching prevent accidental thundering herds.

## Future enhancements

- Edge caching (e.g. Workers) for read-heavy, geography-sensitive paths
- Predictive cache warming from traffic and merchandising signals
- Persisted queries to trim payloads and execution cost
