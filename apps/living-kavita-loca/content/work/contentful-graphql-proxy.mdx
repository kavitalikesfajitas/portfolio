# Contentful GraphQL Proxy

**Role:** Technical owner — RFC, epic, multi-sprint delivery  
**Tech Stack:** TypeScript · Node.js · GraphQL · Apollo Server · Express · Redis · AWS

---

**TL;DR:** I turned a growing **REST façade over Contentful GraphQL**—the legacy **`api/content`** Lambda zoo—into a **single, honest GraphQL BFF**: **RFC → Jira epic → tickets → a little over two sprints → done**, starting with a **Next.js Pages API** proof and maturing into a **production-shaped Express proxy** (optional **Redis**, health, CORS, telemetry hooks) that **PDPs could actually scale on**.

## Overview

This is the kind of project that shows **ownership beyond the IDE**. I did not “just implement an endpoint.” I **wrote the internal RFC** (*Replace Content-APIs with a single GraphQL Apollo proxy for Contentful*), **created the Jira epic**, **wrote the implementation tickets**, and **carried the program** from first merge through **just over two sprints** to a credible production story.

The technical villain was familiar and expensive: **`api/content`** looked like a clean **OpenAPI / REST** catalog, but every route still boiled down to **hand-maintained GraphQL** and **`makeItemsRequest`** calls to Contentful. New merchandising surfaces tended to mean **new Lambdas**, **new deployables**, and **new bespoke contracts**—**compounding toil** every time the CMS model moved. **I drove the proxy so that growth curve would stop.**

**Stage 1 (what I shipped first):** a **Next.js** route at `pages/api/contentful/graphql`—**Apollo Server**, schema in repo, **HTTP executor** POST to Contentful, **in-memory LRU** caching, and explicit cache-control defaults. Fast proof, real cache behavior, real security boundary (tokens and space IDs stay server-side).

**Stage 2 (where it had to land for scale):** the same architectural bet in a **standalone Express** service in my monorepo—**`POST /contentful/graphql`**, **Redis-backed** Apollo cache when you need **shared hits across replicas**, **`GET /contentful/health`**, CORS, optional **HTTPS** for local dev, and **CI/Docker**-friendly packaging. One surface for content reads instead of **N** Lambdas pretending to be REST.

## The challenge (why the old shape had to go)

- **Honesty gap** — Teams integrated like it was REST; **Contentful was always GraphQL POST**. That mismatch slowed **query evolution**, **typing**, and **reviews** because the system lied about what it was.
- **Sprawl tax** — **`api/content`** meant **one handler per concern** (`get-page`, `get-collections`, `get-product-by-slug`, …) and **more SAM surface area** whenever the CMS added a shape we had to expose.
- **Platform economics** — Every new endpoint duplicated **auth**, **caching**, **observability**, and **operational muscle memory**. The proxy collapses that into **one place to optimize** and **one place to tune TTLs** against **Contentful’s delivery limits**.
- **Cache reality** — In-process LRU is fine for a **single** Node; **Redis** is how you get **consistent** cache behavior when traffic fans out across instances.

## What I built

### Next.js proof → Express production shape

The **first implementation lived in the web app**; the **standalone service is the same bet** with a host that matches how you run **long-lived** GraphQL at the edge of your platform.

```typescript
const executor = buildHTTPExecutor({
  endpoint: CONTENTFUL_GRAPHQL_BASE_URL,
  method: "POST",
  timeout: 5000,
  headers: { Authorization: `Bearer ${process.env.CF_DELIVERY_CONTENT_TOKEN}` },
  retry: 1,
});

const schema = wrapSchema({
  schema: contentfulSchema,
  executor,
});
```

### Caching, correctness, and ops

- **Apollo cache-control defaults** because **Contentful’s schema does not ship cache hints**—without defaults, you get accidental **thundering herds** and surprise behavior under load.
- **`response-cache`** aligned to those policies so **successful reads** stay **fast** and **predictable**.
- **Redis or in-memory** behind Apollo’s key-value cache—**toggle by environment**, not by rewrite.
- Optional **telemetry** hooks on the Apollo path so **latency and cache behavior** are visible where SREs and on-call already look.
- **`/contentful/health`**, **CORS**, and **local HTTPS** (mkcert) so **storefront dev** matches **prod-ish** constraints.

### How I ran the program (not just the repo)

- **RFC** — Named the **anti-pattern**, staged **Stage 1 / Stage 2**, and grounded caching in **vendor rate-limit reality** so the design was **reviewable**, not vibes.
- **Planning** — **Epic + tickets** sequenced to **prove value early** (Next proof) and **de-risk** the extraction (Express + Redis + ops).
- **Execution** — **A little over two sprints** of focused delivery: proxy pattern, caching defaults, and the **operational hooks** that make Contentful reads a **platform concern**, not a **per-Lambda accident**.

## What I’d repeat on the next platform bet

- **Write the short, blunt RFC** — It turned a recurring gripe into **funded work** with **exit criteria** stakeholders could recognize.
- **Stage the risk** — **Prove on Next** (fast feedback), **extract when the shape is honest** (scale, Redis, ops).
- **Name the wire protocol in the API** — When integration is GraphQL, **own it in the surface**; hiding it behind REST **taxes every future query change**.
- **Default the cache story** — Upstream schemas without hints are normal; **your server must still enforce** sane **TTLs** and **response caching** so you stay inside **delivery limits** and keep **tail latency** under control.

## Future enhancements

- Edge caching (e.g. Workers) for read-heavy, geography-sensitive paths
- Predictive cache warming from traffic and merchandising signals
- Persisted queries to trim payloads and execution cost
