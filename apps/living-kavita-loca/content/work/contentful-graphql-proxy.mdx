# Contentful GraphQL Proxy

**Role:** Technical owner — RFC, epic delivery, standalone service  
**Tech Stack:** TypeScript · Node.js · GraphQL · Apollo Server · Express · Redis · AWS

---

## Overview

**I owned this end to end:** I wrote the internal RFC (*“Replace Content-APIs with a single GraphQL Apollo proxy for Contentful”*), stood up the **Jira epic**, broke the work into **trackable tickets**, and carried it through **a little over two sprints** to **done**—from first merge to a production-shaped service story.

The problem was organizational and technical at once: we had a **content API pattern that translated Contentful’s GraphQL into REST**. That looked convenient to consumers but was **slow to extend** (new content models tended to mean **new endpoints** and repeated backend work), and it **hid** that the real wire protocol was still **GraphQL POST** upstream.

**I wrote the first version as a Next.js endpoint:** a **Pages API** route at `pages/api/contentful/graphql` with **Apollo Server** in front of Contentful—checked-in schema, **HTTP executor** (POST upstream), **in-memory LRU** response caching, and cache-control defaults so we could **prove the proxy, caching, and security boundary** without boiling the ocean. That shipped as **Stage 1** in the RFC. **Stage 2** was intentionally exploratory (e.g. **standalone / serverless** shapes); I **extracted the design** into a standalone **Express** service in my own monorepo: **`POST /contentful/graphql`**, optional **Redis** for a shared response cache (versus in-process LRU on the Next route), **health checks**, CORS, and CI-friendly packaging.

## The Challenge

- **REST-over-GraphQL anti-pattern** — We were wrapping **GraphQL/POST** in **REST-shaped** APIs; that did not scale with how fast merchandising and PDP teams needed to ship new content models.
- **Endpoint sprawl** — Serving a new Contentful model through the old pattern meant more bespoke API surface instead of one intentional contract.
- **Slow query and schema iteration** — Evolving operations, typings, and cache defaults was painful without a single BFF and a honest integration model.
- **Cache topology** — In-process caching worked for a single Node instance; **Redis** was the next step for consistent hits across replicas and deploys.
- **Operational clarity** — We needed a small surface (`/contentful/graphql`, `/contentful/health`) and sane defaults for TTLs and telemetry.

## Solution

### From Next.js route to standalone service

The **first implementation lived in the Next.js app**; the **standalone service is the same architectural bet** with a different host. The core idea stayed the same: **load Contentful’s schema from the repo**, **wrap** it, and **delegate** execution to Contentful’s HTTP API with a bearer token. Moving to Express keeps that contract but pulls it out of the web app into a long-lived process where **Redis-backed Apollo caching** is a first-class option.

```typescript
const executor = buildHTTPExecutor({
  endpoint: CONTENTFUL_GRAPHQL_BASE_URL,
  method: "POST",
  timeout: 5000,
  headers: { Authorization: `Bearer ${process.env.CF_DELIVERY_CONTENT_TOKEN}` },
  retry: 1,
});

const schema = wrapSchema({
  schema: contentfulSchema,
  executor,
});
```

### Caching and observability

- **Apollo Server** with **cache-control defaults** (Contentful’s schema does not ship cache hints; defaults keep behavior predictable).
- **`response-cache`** so successful query results are cached in line with those policies.
- **Redis or in-memory** cache implementation behind Apollo’s key-value cache interface, selectable per environment.
- Optional **OpenTelemetry-style** Apollo plugin hooks for production metrics when enabled.

### Delivery

- **`GET /contentful/health`** for probes and sanity checks.
- **CORS** configured for known storefront origins.
- **HTTPS in local dev** (optional mkcert paths) when frontends require a trusted origin.

### How I drove it (program, not just code)

- **RFC** — Documented context, goals, and a staged plan: **Stage 1** (Next API proxy + guardrails) and **Stage 2** (extractable / alternate hosting), including **Contentful rate-limit** notes so caching strategy stayed grounded in vendor reality.
- **Planning** — Created the **Jira epic**, wrote and linked **implementation tickets**, and sequenced work so we could **prove value early** and **de-risk** extraction.
- **Execution** — Delivered across **just over two sprints**: shipped the proxy pattern, caching defaults, and the operational hooks the team needed to treat Contentful reads as a first-class platform concern.

## Key Learnings

- **Write the RFC before the hype** — A short, blunt doc about the **anti-pattern** and **staged rollout** turned a gripe into a **funded epic** with clear exit criteria.
- **Name the integration honestly** — When the wire protocol is GraphQL POST, **API shape and team habits** should match, or iteration cost stays hidden.
- **Schema-in-repo + executor** — Treating Contentful as an implementation detail behind a stable local schema speeds up reviews and codegen.
- **Cache defaults matter** — Without explicit cache policy on the upstream schema, **explicit server-side max-age** and response caching keep you inside **Contentful’s delivery limits** and avoid thundering herds.

## Future enhancements

- Edge caching (e.g. Workers) for read-heavy, geography-sensitive paths
- Predictive cache warming from traffic and merchandising signals
- Persisted queries to trim payloads and execution cost
