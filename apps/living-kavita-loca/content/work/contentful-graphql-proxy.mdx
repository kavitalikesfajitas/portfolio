# Contentful GraphQL Proxy

**Role:** Technical owner — RFC, epic, multi-sprint delivery  
**Tech Stack:** TypeScript · Node.js · GraphQL · Apollo Server · Express · Redis · AWS

---

## About

At Nike, a lot of Contentful reads were hiding behind `api/content`.

On paper, that looked like a nice REST API. In reality, every route was still hand-written GraphQL to Contentful. Need a new content shape? Add another handler. Need a new field? Backend change. Need a slightly different query? Another little deployment for something that should have been a schema problem.

It worked, but it kept growing in the wrong direction.

I replaced that sprawl with a single GraphQL proxy: one endpoint, one cache story, one place to observe and tune Contentful traffic.

The first version was a quick Next.js proof of concept. That was useful because it proved the shape fast. But it also made the limit obvious: in-process cache inside a web route was not going to hold up for `swoosh.nike` traffic. Once you care about replicas, cold starts, and shared cache hits, "just put an LRU in the route" stops being cute.

So I wrote the RFC, created the Jira epic and tickets, and led the work over a little more than two sprints. The production version became a dedicated Express + Apollo service with Redis, health checks, CORS, local HTTPS support, and telemetry.

---

## The Problem

The old setup had a few problems that all fed each other:

- It looked like REST, but it was really GraphQL wearing a jacket.
- Backend owned too much of the content query shape.
- Small CMS changes could turn into API deployments.
- The Lambda surface area kept expanding.
- Caching was scattered, local, and hard to reason about under real traffic.

## Before and after

Before, storefronts called a growing list of REST-shaped endpoints like `get-page`, `get-collections`, and `get-product-by-slug`. Each endpoint had its own handler, its own OpenAPI surface, and its own hand-maintained GraphQL call to Contentful.

After, clients called one endpoint: `POST /contentful/graphql`.

The proxy loaded the Contentful schema from the repo, wrapped it, and forwarded requests with server-only credentials. Cache policy, timeouts, and telemetry lived in one place instead of being re-learned per Lambda.

```text
                    ┌─────────────────────────────────────────┐
  Storefronts  ───► │  Legacy: many REST Lambdas (api/content) │
  & BFFs            │  each with its own GraphQL to Contentful │
                    └─────────────────────┬───────────────────┘
                                          ▼
                               Contentful GraphQL (CDA)

                    ┌─────────────────────────────────────────┐
  Storefronts  ───► │  Proxy: one Apollo BFF                    │
  & BFFs            │  POST /contentful/graphql                 │
                    └─────────────────────┬───────────────────┘
                                          ▼
                               Contentful GraphQL (CDA)
```

Same upstream. Much better ownership model.

## What I built

### The first version

I started with a Next.js route because I wanted to prove the idea before asking everyone to care about it.

That POC used Apollo inside a Pages API route and a small in-memory cache. It was enough to answer the important question: can we expose a clean GraphQL surface while keeping Contentful credentials and vendor details server-side?

Yes.

But it was not the final architecture. The POC was still tied to the web app, and the cache lived inside one process. For the traffic profile we cared about, especially PDP traffic on `swoosh.nike`, we needed a dedicated service with shared cache behavior.

### The production shape

The production version became a standalone Express server running Apollo:

- `POST /contentful/graphql` for content queries
- `GET /contentful/health` for liveness
- Redis-backed cache behavior across instances
- CORS and optional local HTTPS for realistic browser testing
- Docker/CI packaging so it could run like the rest of the platform

```typescript
const executor = buildHTTPExecutor({
  endpoint: CONTENTFUL_GRAPHQL_BASE_URL,
  method: "POST",
  timeout: 5000,
  headers: { Authorization: `Bearer ${process.env.CF_DELIVERY_CONTENT_TOKEN}` },
  retry: 1,
});

const schema = wrapSchema({
  schema: contentfulSchema,
  executor,
});
```

That code is doing three jobs:

- Load a checked-in Contentful schema so reviewers and clients have a real contract.
- Use an HTTP executor to forward operations to Contentful with a bounded timeout and retry.
- Let Apollo validate and execute against the local schema while Contentful stays behind the proxy.

### The cache work

The cache was the part that mattered most.

Contentful is fast when you stay on the cached path. It is much less forgiving when launch traffic starts turning into uncached upstream reads. So the proxy needed to make caching boring and predictable.

I used Apollo cache control with a default max age, response caching for successful queries, and a layered cache with memory first and Redis second. Hot keys could stay close to the process, while shared entries survived across replicas.

One small but important detail: Apollo `cache` and `documentStore` are not the same thing. Response caching, APQ, and other Apollo cache consumers use `cache`; parsed-and-validated operation reuse belongs to `documentStore`. I treated those as separate knobs instead of pretending one cache solved every problem.

```typescript
const responseLayer = new Cacheable({
  primary: responseMemoryStore,
  secondary: responseRedisStore,
  nonBlocking: true,
});

const apolloCache = new KeyvAdapter(
  new Keyv({
    store: responseLayer,
    namespace: "contentful-cache",
  }),
  { disableBatchReads },
);

const documentStore = createParsedQueryDocumentStore({
  store: parsedQueryRedisStore,
  namespace: "contentful-document-store",
});

const server = new ApolloServer({
  schema,
  cache: apolloCache,
  documentStore,
  plugins: [ApolloServerPluginDrainHttpServer({ httpServer })],
});
```

### Proving it without direct Redis access

This was the least glamorous part and probably the most real.

I could not just SSH into managed Redis and poke around. I had to prove cache behavior from the application edge.

So I added debug hooks behind `DEBUG_PROXY`, ran local Redis with Docker, watched `redis-cli monitor`, and compared that with the proxy logs while sending real GraphQL queries. Then I used repeated warm/cold request patterns to prove when reads were coming from memory, Redis, or Contentful.

It was not fancy. It was the kind of debugging that makes you trust the system after you ship it.

Representative debug pattern:

```typescript
if (debugProxy) {
  layeredCache.onHook(CacheableHooks.AFTER_SET, ({ key, ttl }) => {
    console.log(`set ${key} ttl=${ttl}`);
  });
  layeredCache.onHook(CacheableHooks.AFTER_GET, ({ key, result }) => {
    console.log(`get ${key} hit=${Boolean(result?.value)}`);
  });
}
```

### The Redis decision

I also wrote the Redis decision doc. The choice came down to provisioned ElastiCache versus ElastiCache Serverless.

We chose serverless because it matched the shape of the service: variable traffic, managed failover, less capacity planning, and pay-per-use economics. The tradeoff is that you do not get every low-level knob you would with a provisioned setup. That was acceptable here because the important work was making cache behavior observable and safe, not hand-tuning a cluster.

### Hardening

The proxy also cleaned up a few things that had been spread around before:

- Contentful tokens stayed server-side.
- The schema lived in the repo, so reviews could see the contract.
- Introspection and landing pages stayed off in production.
- Timeouts and retries were bounded so a bad upstream day did not pile up forever.
- Health checks were cheap and did not need to hit Contentful.

## How I ran the work

This was not just a code change. I had to make the work legible enough for people to fund it.

The POC gave me something concrete to show. The RFC turned the recurring gripe into a staged plan. The Jira epic split the work into server extraction, Redis, cache behavior, telemetry, and delivery pieces. Then I drove the implementation across a little more than two sprints.

That order mattered. It kept the project from becoming "let's rebuild content infra because GraphQL feels nicer." The point was simpler: fewer handlers, safer cache behavior, better latency, and less backend work for every new content query.

The numbers are nice, but the bigger win was operational.

New Contentful-backed experiences did not need another `api/content` Lambda. TTLs and telemetry lived together. Frontend and platform teams could standardize on GraphQL operations and generated types instead of pretending the system was REST all the way down.

## What I’d do again

- Prove the shape cheaply before writing the big plan.
- Make the RFC short and blunt.
- Name the real protocol. If the system is GraphQL, let it be GraphQL.
- Treat caching as part of the API design, not a performance sprinkle at the end.

## Future enhancements

- Edge caching (e.g. Workers) for read-heavy, geography-sensitive paths
- Predictive cache warming from traffic and merchandising signals
- Persisted queries to trim payloads and execution cost
