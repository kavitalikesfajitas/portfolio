    # Company logo generation

    The company marks make Dammit easier to scan. A person should be able to
    glance at the company list and separate Stripe from Figma from Vercel
    without reading every word. The logos are not decoration; they are
    wayfinding.

    <LogoDecisionPreview />

    ## The decision

    For the current curated seed list, logos can live in
    `public/images/logos`. They are part of the app artifact, they are easy to
    inspect in the repo, and the UI can render stable public paths from
    `manifest.json`.

    That is the right tradeoff while companies are code-reviewed. If a company
    is added to `COMPANY_BOARD_TOKENS`, the build should make sure the visual
    asset story is complete before the app ships.

    ## How it works today

    The implementation lives in:

    - `scripts/fetch-company-logos.ts`
    - `next.config.ts`
    - `public/images/logos/manifest.json`

    The script derives a likely domain from each board token, tries a few public
    favicon/logo services, saves the first real image it finds, and writes a
    manifest the app can consume.

    The sources are deliberately simple:

    ```txt
    icon.horse
    Google favicon service
    DuckDuckGo icon service
    ```

    Existing logo files are useful as durable fallbacks. If a fresh fetch fails
    but the repo already has a logo for that company, the build can still ship
    a complete UI.

    Read the script:
    [scripts/fetch-company-logos.ts](https://github.com/kavitalikesfajitas/portfolio/blob/main/apps/dammit-i-need-a-new-job/scripts/fetch-company-logos.ts).

    ## Why not write to `public` later?

    There are three different operations that sound similar:

    ```txt
    Write to the repo before deploy
    Write to the deployed app filesystem after deploy
    Write to an external asset store after deploy
    ```

    Writing to the repo before deploy is the seeded-company workflow. It is
    reliable because the logo becomes part of the deployed app.

    Writing to the deployed app filesystem is not a good dynamic-company model.
    It may work in some long-lived runtimes, but it is fragile for modern
    serverless or immutable deployments. A written file may disappear, may not
    be shared across instances, or may never be served by the static asset
    layer.

    So the position is not "`public` is bad." The position is:

    ```txt
    public/images/logos is great for seeded repo-owned assets.
    It is not durable storage for companies approved after deploy.
    ```

    ## The future model

    If Dammit moves toward requested or approved companies, logo resolution
    should move to approval time:

    ```txt
    Approve company
            ↓
    Resolve logo candidates
            ↓
    Owner reviews or overrides
            ↓
    Store final logo in S3, Vercel Blob, or similar
            ↓
    Store logoUrl with the approved company record
            ↓
    Pages render the stored logoUrl
    ```

    In that model, pages stay boring. They do not call favicon services, upload
    files, or guess domains. They only read a reviewed `logoUrl`.

    ## Decision for now

    Keep build-time logo generation for the curated seed list.

    When dynamic company approvals exist, reuse the current resolver as an
    approval-time helper, store reviewed logos in durable asset storage, and put
    the final `logoUrl` on the approved company record.
